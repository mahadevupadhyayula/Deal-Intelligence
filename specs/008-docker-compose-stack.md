# Spec 008 — Docker Image & Compose Stack (api, worker, migrate, Postgres, Redis)

**Status:** Done; Gates 1, 2 (N/A, equivalence evidence) and 3 pass
**Phase:** Slice 1 (Lead Research) — Deploy: local · **Depends on:** 001–007

## Objective
Package the system so the whole Slice 1 stack runs with one command, the same way on any machine: one hardened container image (api, worker, migration and operator tools as different commands), plus a `docker-compose.yml` with Postgres+pgvector, Redis, a one-shot `migrate` job, the `api` and a scalable `worker`. This is step one of the learning path to the cloud: everything later (observability 009, local Kubernetes + KEDA 010, Terraform plan 011) reuses this image and its environment contract. No application behaviour changes; the deliverable is a reproducible, least-privilege, verifiable runtime.

## Decisions Taken
- **One image, several commands** (`uvicorn`, `arq`, `python -m agents.migrate`, `python -m agents.admin|evals`). Same code, one build, one thing to scan and version. Trade-off: the API image also carries LangGraph/LangChain although it never runs them (noted in Spec 003's `job_kinds.py`); a slimmer API image is a later optimisation if size matters.
- **Multi-stage build with two final targets:** `runtime` (api, worker, migrate: no tests, no datasets) and `tools` (adds `evals/` datasets and `tests/fixtures/` so `python -m agents.evals` and the golden suite run in a container). Compose uses `runtime` for services and `tools` only under the `tools` profile.
- **Reproducible dependencies:** commit `requirements.lock` generated by `uv pip compile` (with the `llm-openai` and `llm-anthropic` extras) and install from it in the image. `pyproject.toml` keeps ranges for development; the lock pins what ships. Regenerating the lock is an explicit, reviewed step.
- **Least privilege for secrets:** no `env_file`. Each service lists exactly the variables it needs under `environment:`. `ADMIN_DATABASE_URL` (superuser) is given **only** to `migrate` and the `tools` profile, never to `api` or `worker`; provider keys go only to `worker` (and `tools`); `api` gets no LLM/search keys. Nothing secret is baked into the image; a test asserts `.env` is excluded and no `ENV`/`ARG` carries a secret.
- **Required variables fail fast:** `${VAR:?message}` for `POSTGRES_PASSWORD` and `APP_USER_PASSWORD` so a missing value stops `compose up` with a clear message instead of starting with an empty password. No default passwords in the compose file.
- **Does not collide with existing dev containers:** the stack's host ports default to `5433` (Postgres), `6380` (Redis) and `8000` (API), overridable via `POSTGRES_HOST_PORT`, `REDIS_HOST_PORT`, `API_HOST_PORT`, and bound to `127.0.0.1` only. Inside the compose network services talk by name (`postgres`, `redis`) on the standard ports. Project name is fixed (`name: deal-intelligence`) so volumes and networks are predictable.
- **Redis must never evict:** `--maxmemory-policy noeviction` and `--appendonly yes` with a volume. The queue, rate-limit counters and job state live there; silent eviction would drop work or reset limits.
- **Startup order is explicit and safe:** `postgres`/`redis` healthy -> `migrate` completes successfully -> `api` and `worker` start. Migrations are already concurrency-safe (advisory lock), so `--scale worker=N` is safe.
- **Workers are stateless and scalable by design:** no `container_name`, no host ports, so `docker compose up --scale worker=3` works. This is the local rehearsal of KEDA scaling (Spec 010) and exercises the per-tenant advisory-lock admission under real concurrency.
- **Container hardening (applies to api, worker, migrate):** non-root numeric user, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, read-only root filesystem with a `tmpfs` for `/tmp`, restart policy `unless-stopped` for api/worker, resource limits set (memory/CPU, configurable). Postgres/Redis keep their image defaults except for the settings above.
- **Health model matches Kubernetes (Spec 010):** api healthcheck calls `/healthz` (liveness) and `depends_on` waits for it; readiness (`/readyz`) is checked by the smoke test. Worker health uses ARQ's built-in check (`arq --check`), which needs `health_check_interval` set on `WorkerSettings` (a one-line change in `workers/settings.py`).
- **Graceful stop:** `stop_grace_period` for the worker is set just above `JOB_TIMEOUT_SECONDS`; Gate 3 records what actually happens to an in-flight job on `docker compose stop worker` (ARQ's SIGTERM behaviour is verified, not assumed) and the result is written into the Implementation Notes.

## Technical Requirements

### 1. Files
- `infra/docker/Dockerfile` — multi-stage: `builder` (python:3.11-slim-bookworm, creates a venv from `requirements.lock`), `runtime` (copies venv + `agents/ api/ workers/ migrations/`, `USER 10001`, `PYTHONUNBUFFERED=1`, `PYTHONDONTWRITEBYTECODE=1`), `tools` (extends `runtime` with `evals/` and `tests/fixtures/`). Base image tag pinned (digest recorded in Implementation Notes). Default `CMD` prints usage; compose supplies commands.
- `.dockerignore` (repo root, the build context) — excludes `.env*` (but not `.env.example`), `.git`, `.venv`, `__pycache__`, `evals/reports`, `docs`, `tests` (except what `tools` copies is added explicitly in the Dockerfile from an allow-list), `deal_intelligence.egg-info`.
- `requirements.lock` — generated with `uv pip compile pyproject.toml --extra llm-openai --extra llm-anthropic -o requirements.lock`.
- `docker-compose.yml` (repo root) — services:

  | Service | Image target | Command | Notable config |
  |---|---|---|---|
  | `postgres` | `pgvector/pgvector:pg16` | default | `POSTGRES_PASSWORD`, `POSTGRES_DB=deal_intel`, named volume, `pg_isready` healthcheck, localhost-only published port |
  | `redis` | `redis:7-alpine` | `redis-server --appendonly yes --maxmemory-policy noeviction` | named volume, `redis-cli ping` healthcheck, localhost-only published port |
  | `migrate` | `runtime` | `python -m agents.migrate` | `ADMIN_DATABASE_URL`, `APP_USER_PASSWORD`; `restart: "no"`; exits 0 |
  | `api` | `runtime` | `uvicorn api.main:app --host 0.0.0.0 --port 8000` | `DATABASE_URL` (app_user), `REDIS_URL`, limits and trace-redaction settings; no provider keys |
  | `worker` | `runtime` | `arq workers.settings.WorkerSettings` | `DATABASE_URL`, `REDIS_URL`, `LLM_MODEL`, `TAVILY_API_KEY`, `OPENAI_API_KEY`/`ANTHROPIC_API_KEY`, LangSmith vars; scalable |
  | `tools` (profile `tools`) | `tools` | `python -m agents.admin` / `python -m agents.evals` | `ADMIN_DATABASE_URL`, `DATABASE_URL`, provider keys; run with `docker compose run --rm tools ...` |

- `workers/settings.py` — add `health_check_interval = 30` (nothing else changes).
- `.env.example` — document the compose variables (`POSTGRES_PASSWORD`, `*_HOST_PORT`, resource limits) with `CHANGE_ME` placeholders and a note that compose builds the in-network URLs itself.
- `scripts/compose_smoke.sh` — the Gate 3 script (build, up, wait, tenant/key creation, `echo` job, isolation check, restart persistence, scale-out, teardown); exits non-zero on the first failed assertion and never prints key values.
- `docs/local-stack.md` — a short runbook: first run, ports, creating a tenant and key, submitting a job, logs, scaling, reset (`down -v`), and the secret-handling rules.

### 2. Environment contract (reused by Specs 010 and 011)
The container reads configuration only from environment variables (the same `pydantic-settings` fields as today). The in-network URLs are assembled in compose from `POSTGRES_PASSWORD` and `APP_USER_PASSWORD`; Kubernetes (Spec 010) will source the same variables from Secrets/ConfigMaps, and Terraform (Spec 011) from RDS/ElastiCache outputs. A table in `docs/local-stack.md` lists every variable, which service needs it, and whether it is secret.

### 3. Constraints from CLAUDE.md
- Zero hardcoded secrets: compose and Dockerfile contain no password/key literals; `.env` is never copied into an image or into the build context.
- Never block FastAPI / `tenant_id` rules are unchanged; the smoke test re-proves tenant isolation through the containerised stack (RLS as `app_user`, not superuser).
- Every new code file (the smoke script, any Python) gets a WHAT/WHERE/WHY header comment/docstring; the Dockerfile and compose file carry comments explaining the trade-offs above.

## 3-Gate Verification & Acceptance Criteria

### Gate 1 — Unit (`pytest -v`)
- [ ] Static checks on `docker-compose.yml` (PyYAML parse): no literal password/key values; `postgres`/`redis` published only on `127.0.0.1`; required variables use `:?`; every app service has a non-root user, `cap_drop: ALL`, `no-new-privileges`, a healthcheck (api/worker/postgres/redis) and a restart policy where specified; `migrate` is `service_completed_successfully` for `api` and `worker`; `ADMIN_DATABASE_URL` appears only in `migrate` and `tools`; provider keys appear only in `worker` and `tools`; Redis command contains `noeviction`; worker has no `container_name` or host ports.
- [ ] Static checks on the Dockerfile and `.dockerignore`: final stages set a numeric non-root `USER`; no `COPY .env`, no `ENV`/`ARG` with secret-like names; `.dockerignore` excludes `.env`, `.git`, `.venv`.
- [ ] `requirements.lock` parses and pins (`==`) the core packages (fastapi, uvicorn, arq, psycopg, pydantic, langgraph, langchain, langsmith, tavily-python, langchain-openai, langchain-anthropic).
- [ ] `docker compose config -q` succeeds with a dummy env file (skipped, not failed, if Docker is unavailable).
- [ ] `WorkerSettings.health_check_interval` is set; all existing tests still pass (347 baseline); `ruff` clean.
- [ ] `tenant_id` isolation: no application code changes; the existing RLS tests are the proof, and the containerised isolation check is in Gate 3.

### Gate 2 — Agent Behavior
- N/A for agent logic: no agent, prompt, guardrail or scoring code changes. As equivalence evidence only, the free scripted golden suite is run **inside the `tools` image** (`docker compose run --rm tools python -m agents.evals run golden`) and must give 22/22, proving the packaged image behaves like the dev environment.

### Gate 3 — Live Smoke Test (`scripts/compose_smoke.sh`)
- [ ] `docker compose up -d --build --wait` -> `postgres`, `redis`, `api`, `worker` healthy; `migrate` exited 0; `docker compose ps` shows no restarting container.
- [ ] `curl -s localhost:8000/healthz` -> `{"status":"ok"}` and `/readyz` -> 200 with `postgres` and `redis` both `ok`; stopping Redis makes `/readyz` 503 while `/healthz` stays 200 (liveness/readiness split), and it recovers when Redis returns.
- [ ] Create two tenants and keys via the `tools` service; submit an `echo` job as tenant A, poll to `succeeded`; tenant B cannot read A's job (404); as `app_user` through `psql` inside the Postgres container, `SELECT` without `app.tenant_id` set returns 0 rows (forced RLS) and `relforcerowsecurity` is true on tenant tables.
- [ ] Re-running `compose up` is a no-op for migrations ("up to date"); `docker compose down` then `up` keeps data (named volume); `down -v` wipes it.
- [ ] Queue durability: stop the worker, submit 3 `echo` jobs (accepted, `queued`), start the worker, all 3 reach `succeeded`.
- [ ] Scale-out: `--scale worker=3`, submit 12 `echo` jobs for one tenant with `TENANT_MAX_ACTIVE_JOBS` low enough to refuse some: accepted + refused counts match the cap, every accepted job succeeds exactly once (no duplicates), no tenant exceeds its cap.
- [ ] Secret hygiene: `docker image history`/`docker inspect` show no secret in the image or its env; `docker compose config` run on the `api` service shows no admin URL or provider key; container logs contain no key value.
- [ ] Record `docker images` size, cold build time, and the observed `docker compose stop worker` behaviour for an in-flight job.

## Implementation Notes (as built, 2026-11-23)
**Deviations from the draft, and why**
- Only `migrate` carries `build:`; `api` and `worker` reference the same image with `pull_policy: never`. Three services building one tag in parallel raced ("image already exists") on the first build.
- Added an opt-in delay to the free `echo` job (`delay_seconds`, clamped by `ECHO_MAX_DELAY_SECONDS`, default 0 = disabled) so scale-out and shutdown can be tested without provider spend; Spec 010 reuses it to watch KEDA scale on queue depth.
- `stop_grace_period` is 30s, not "just above the job timeout" (see finding 1).
- Gate 1 grew from the draft: the worker-cancellation fix and the echo delay have unit tests (367 tests total).

**Findings from the live smoke test**
1. **A stopped worker stranded its in-flight job in `running` forever.** On SIGTERM ARQ cancels the job immediately (it does not drain); the row never left `running`, and stranded rows count toward the tenant's active-job cap, so repeated deploys would eventually lock a tenant out. Fixed in `workers/tasks.py`: a cancelled run is recorded `failed: worker stopped before the job finished; resubmit` (and its provider usage is still flushed), then the cancellation is re-raised. Proven by a unit test (mutation-checked) and by smoke step 7.
2. **Still open (follow-ups):** (a) a hard kill (SIGKILL/OOM) cannot be caught, so a reaper for stale `running` jobs is needed (cross-tenant maintenance needs an admin-role task or a SECURITY DEFINER function, so it is its own design); (b) true draining on shutdown (stop taking jobs, let the current one finish) matters for KEDA scale-down in Spec 010, because every scale-down currently wastes the in-flight LLM run.

**Measured:** image size 506 MB (runtime) / 507 MB (tools); first build including base-image pulls about a minute; the full smoke run takes about two minutes. Base image: `python:3.11-slim-bookworm` (tag pinned; digest not pinned, noted for Spec 011).
