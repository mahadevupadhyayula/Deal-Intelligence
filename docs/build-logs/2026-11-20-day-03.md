## 2. What it achieves
Requests never run agent work: the API records a job, enqueues ids only, and returns 202. The worker re-reads the job under the tenant's RLS session, so a forged tenant on a queue message touches nothing. Tenant identity comes only from a hashed API key.

## 3. Fit in the framework
Upstream: Specs 001/002 (schemas, config, RLS repos). Downstream: Specs 004–008 register agent handlers in `JOB_HANDLERS`; Spec 007 uses `make_thread_id` for PostgresSaver; Spec 010 adds webhook idempotency/rate limits in front of this path; Spec 014/016 containerise and KEDA-scale the worker.

## Notes / decisions
- Decisions as recommended in the spec: hashed per-tenant API keys; async session + async `JobRepo` (sync repos untouched); every job persisted in Postgres.
- Insert-then-enqueue is not atomic: on Redis failure the job is marked `failed` and the API returns 503. An outbox is a future upgrade.
- `max_tries=1`: no automatic retries until agents define retry safety. Duplicate deliveries are no-ops (only `queued` jobs run).
- Pool-based tests commit real rows, so they clean up as admin instead of rolling back.
- Local infra: `docker run -d --name deal-intel-redis -p 6379:6379 redis:7` (Spec 014 replaces with compose). Smoke rows and the minted key were deleted afterwards.
